title: Track
description: "Represents an audio, MIDI, return, or main track in a Live Set."
---

Represents an audio, MIDI, return, or main track in a Live Set. The `Track`
class hosts the track's clip slots, devices, mixer, and routing — not all
properties are supported by every track type, and individual members are
marked accordingly.


### <span class="sig"><span class="sig-name" data-path="Live.Track.">Track</span><span class="sig-base"><a class="sig-base-link" href="/LiveAPI/modules/track/#devicecontainer" data-base="DeviceContainer" aria-label="DeviceContainer"></a></span></span><a class="lom-badge" href="/LiveAPI/live-object-model/" title="This is a LomObject — see the LomObject page for the universal identity / lifetime model" aria-label="LomObject"></a>

This class represents a track in Live. It can be either an Audio track, a MIDI Track, a Return Track or the Main track. The Main Track and at least one Audio or MIDI track will be always present. Return Tracks are optional.<sup class="source-marker" tabindex="0" aria-label="from Live's runtime docstring"><span class="source-marker-tooltip" role="tooltip"><span class="sm-note">From Live's runtime docstring.</span></span></sup>

### <span class="sig"><span class="sig-name" data-path="Live.Track.">DeviceContainer</span></span><a class="lom-badge" href="/LiveAPI/live-object-model/" title="This is a LomObject — see the LomObject page for the universal identity / lifetime model" aria-label="LomObject"></a>

Phantom base in the LOM type system. `Track` and `Chain` both
register `DeviceContainer` as their direct Python superclass via
Boost.Python's `bases<>` mechanism — `Track.__mro__` includes it,
`isinstance(track, DeviceContainer)` is True — but Boost binds the
shared methods and properties on each concrete subclass rather
than on the base. Result: real Python inheritance, structurally
empty class.

**Members are redefined on each subclass.** The shared surface
(`color`, `color_index`, `mute`, `muted_via_solo`, `name`, `solo`,
`delete_device`, `duplicate_device`, `insert_device`) is declared
independently on `Track` and `Chain`, each carrying its own
runtime docstring. The declarations live on the subclasses; this
class is the structural parent that holds them together for
`isinstance` purposes only.

**Idiomatic code ignores it.** Ableton's own corpus and the M4L
docs contain zero references to `DeviceContainer` — the
convention is `isinstance(c, (Live.Track.Track, Live.Chain.Chain))`
rather than testing against the common base. Treat it as an
implementation detail of the LOM type system, not a class to
program against.<sup class="source-marker" tabindex="0" aria-label="view runtime docstring"><span class="source-marker-tooltip" role="tooltip"><span class="sm-label">Runtime docstring</span><span class="sm-raw">This class is a common super class of Track and Chain</span></span></sup>
